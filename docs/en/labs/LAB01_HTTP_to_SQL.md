# LAB01 — From HTTP Request to SQL Server

## Objective
Trace the full path **HTTP request → ASP.NET Core → EF Core → SQL Server** and inspect the SQL generated by the ORM.

## Time
35–40 min.

## Before you start
- Docker and the API must be running.
- `EfCoreDbaLab` must be created by `Setup-Lab.ps1` / `Setup-Lab.sh`.
- Prepare `Workshop.Api.http` or Swagger and a SQL connection in VS Code.

## Steps
1. Start the environment and API.
2. Call `GET /workshop1/customers-bad`.
3. In the **`dotnet run` console** find `Microsoft.EntityFrameworkCore.Database.Command`.
4. Copy the SQL and identify the main table, JOIN, selected columns, and TOP.
5. Open `Workshop1Endpoints.cs` and find `Include` + `Take(100)`.
6. Identify what composes the query and what causes execution.
7. In VS Code connect to `localhost,14333` / `EfCoreDbaLab` and run the SQL copied from the EF Core log.

Leave `customers-good` for LAB03 unless the instructor says otherwise.

## What to record
- endpoint,
- generated SQL,
- main table and JOINs,
- selected columns,
- materialization method,
- a short answer: what actually reaches SQL Server?

## Expected result
SQL Server does not see C# or LINQ. It sees the final SQL, parameters, and transactional behaviour produced by the application.

## Exit criterion
You can connect one HTTP request to its generated SQL and point to the place in code where the query is executed.

## If the result is different
- No SQL in the console: make sure you are watching `dotnet run`, not the SQL Server container log.
- Endpoint does not respond: verify `GET /` and port `5000`.
- SQL connection fails: verify port `14333` and the container state.

## Questions
- Does `Include()` execute SQL by itself?
- What exactly reaches SQL Server?
- How do you find SQL generated by EF Core?
