# LAB11 — Incident Investigation: The Endpoint Is Slow

## Objective
Carry out a full diagnosis without starting from the C# code.

## Time
45–50 min.

## Before you start
- LAB10 should be complete.
- The API and Query Store must be working.
- Prepare `sql/05_Diagnostics.sql`, Actual Execution Plan, and the `dotnet run` log.

## Incident
> Users report that `/workshop4/customer/123/orders-bad` is slow and sometimes times out.

Customer **123** is intentionally hot: many orders, wide `Notes`, and order lines. Compare query shape and logical reads, not a single timing value.

## Tasks
SQL Server first:
1. Find the query in Query Store by SQL shape, not by fixed `query_id`.
2. Check execution count, logical reads, CPU, and duration.
3. Open the actual plan and identify tables plus Scan/Seek/Lookup operators.
4. Assess the returned graph width (`Customers` × `Orders` × `OrderLines`, including `Notes`).
5. Call `GET /workshop4/customer/123/orders-nplus1` and count `Database.Command` lines in the `dotnet run` console.
6. Only then inspect the C# Include graph.
7. Compare with `GET /workshop4/customer/123/orders-good` using a manual URL or `Workshop.Api.http` because it is intentionally hidden from Swagger.

## What to record
- symptom,
- Query Store evidence,
- plan and logical reads,
- N+1 round-trip count,
- root cause,
- proposed fix,
- validation method.

## Report
1. Symptom.
2. Evidence.
3. Root cause.
4. Fix.
5. How improvement was confirmed.

## Exit criterion
You can move from the incident report to a concrete SQL/workload pattern and justify the fix with evidence rather than intuition.

## If the result is different
- The expected Query Store entry is missing: regenerate workload and identify by SQL shape.
- `orders-good` is missing from Swagger: that is intentional.
- Round-trip count differs: count only `Database.Command` entries generated by one N+1 request.
