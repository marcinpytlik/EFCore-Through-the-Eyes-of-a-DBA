# LAB06 — Query Shape and SARGability

## Objective
Show how predicate shape affects index usage in both SQL and EF Core.

## Time
30–35 min.

## Before you start
- Workshop 2 should be in the state left by LAB05.
- `IX_Customers_Name` should already exist from setup.
- Prepare VS Code with Actual Execution Plan and `Workshop.Api.http`.

## Preparation
Verify the baseline index instead of creating a duplicate:
```sql
SELECT name, type_desc
FROM sys.indexes
WHERE object_id = OBJECT_ID(N'dbo.Customers')
  AND name = N'IX_Customers_Name';
```

## Steps
1. Compare a direct `Name = @name` predicate with `UPPER(Name) = UPPER(@name)` using `SET STATISTICS IO/TIME` and Actual Execution Plan.
2. Call:
   - `GET /workshop2/customers/search-bad/Customer%20123`
   - `GET /workshop2/customers/search-good/Customer%20123`
3. Compare generated SQL, access operator, and logical reads.
4. Focus on Scan vs Seek and query shape rather than a single timing value.

## What to record
- SQL for direct equality and `UPPER()`,
- access operator for each form,
- logical reads,
- SQL generated by both EF Core endpoints,
- your proposed predicate rewrite.

## Expected result
Functionally correct LINQ such as `ToUpper()` can generate less efficient SQL. SARGability is a predicate-shape concept, not EF magic.

## Exit criterion
You can connect the LINQ expression to generated SQL and explain the Scan/Seek difference from predicate shape.

## If the result is different
- `IX_Customers_Name` is missing: rerun setup instead of creating a second differently named index.
- The plan differs from expectations: inspect collation, actual plan, and reads; do not force a particular result.
- Both endpoints return the same row: that is correct — compare the cost of reaching it.

## Questions
- What does SQL Server see instead of `c.Name.ToUpper()`?
- Why can a function on the indexed column make a Seek harder?
- Can collation change comparison semantics?
